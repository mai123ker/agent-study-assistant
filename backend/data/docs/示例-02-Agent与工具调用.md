# Agent 与工具调用

## Agent 和普通对话的区别

普通对话是「一问一答」：模型收到问题，直接生成答案。

Agent 是「边想边做」：模型先判断自己需不需要外部工具，
需要就请求调用，拿到结果后再判断信息够不够，不够就继续调用，
直到能给出答案为止。

所以 Agent 的本质是一个**带终止条件的循环**，不是什么神秘的东西。

## Function Calling 的工作原理

模型不会执行任何代码。它只是返回一个结构化的 JSON，
告诉你它想调用哪个函数、传什么参数。真正的执行在我们的代码里。

工具的描述（description）质量直接决定调用效果。
描述写得好，模型知道什么时候该调；写得含糊，模型就会该调不调，或者调错工具。

## ReAct 循环

ReAct = Reasoning + Acting，即「推理 + 行动」。

每一轮循环里，模型先推理（要不要调工具、调哪个），
再行动（我们执行工具并把结果喂回去），然后进入下一轮。

## 三个终止条件

Agent 循环必须有终止条件，否则会无限调用、无限烧钱。

第一个条件是拿到最终答案：模型不再请求工具，说明它准备好回答了。
第二个条件是达到最大步数（max_steps），防止模型陷入无效循环。
第三个条件是重复动作检测：如果模型连续两轮用同样的参数调同一个工具，
说明它卡住了，应该主动终止而不是等步数耗尽。

第三个条件是加分项，说明设计者考虑过死循环，而不只是靠步数上限兜底。

## 工具出错怎么办

工具报错不应该抛异常炸掉服务，也不应该直接返回错误给用户。

正确做法是把错误信息格式化后回填给模型，让模型自己决定下一步：
换个参数重试、换个工具、或者直接告诉用户做不到。

这个设计的理由是：工具失败在 Agent 里是**正常业务流**，不是服务器故障。

## 为什么要存 trace

Agent 是非确定性的，同一个问题两次运行可能走不同路径。
出问题时如果没有调用轨迹，就只能靠猜。

所以要把每一步的工具名、参数、耗时、成功与否都记下来，这就是可观测性的雏形。
