## Day 2 —— 多轮对话历史（今天）

**目标：`/api/chat` 从「单轮」变成「记得上一句」。**

### 要改的文件（共 3 个）

**① `backend/app/schemas.py`** —— 请求模型加历史字段

现在 `ChatRequest` 只有 `message` 和 `session_id`（`session_id` 是 Day1 预留的）。
这里要做的是：**让前端可以把之前几轮对话一起传上来**。

思考两个方案，选一个：
- 方案 A：前端每轮传完整 `messages` 列表（简单，前端管状态）
- 方案 B：前端只传 `session_id`，后端用字典存历史（贴近真实产品）

**Day 2 用方案 B。** 因为方案 B 才涉及后端有状态——这是面试要讲的点。

**② 新建 `backend/app/core/memory.py`** —— 内存版会话存储

需要想清楚三件事：
- 用什么数据结构存？（提示：`dict[str, list[dict]]`，key 是 session_id）
- 谁负责生成 session_id？（提示：`uuid4()`，前端没传就新建）
- 历史怎么截断？（**Day 2 先不做**，Day 13 专门做上下文膨胀）

**③ `backend/app/core/llm_client.py`** —— `chat()` 签名要改

现在签名是：
```python
async def chat(self, message: str) -> tuple[str, int]:
```

它只吃一个字符串。现在要它吃整个 `messages` 列表。改成：
```python
async def chat(self, messages: list[dict]) -> tuple[str, int]:
```

`_remote_chat` 里的 payload 已经从 `messages: [{"role": "user", ...}]` 改成直接传：

```python
payload = {
    "model": ...,
    "messages": messages,        # 注意这里的变化
    "temperature": 0.3,
}
```

**`_mock_reply` 也要改** —— 否则测试会挂。让 mock 能反映出「我记得几轮」，
比如回复里带上 `len(messages)`。

**④ `backend/app/api/chat.py`** —— 串起来

流程变成：
```text
拿 session_id（没有就生成）
→ 从 memory 取出该 session 的历史
→ 把本轮 user 消息追加进去
→ 调 client.chat(完整 messages)
→ 把 assistant 回复也存回 memory
→ 返回（含 session_id）
```

### 必须理解的原理

**为什么多轮对话本质就是「把历史塞回 messages」？**
模型本身无状态——它不记得任何事。每次请求你都得把完整对话重发一遍。
这就是为什么对话越长越贵、越慢。

**`system` / `user` / `assistant` 三个角色的作用分别是什么？**
写进 Day 2 面试笔记。

## Day 5 —— 手写 ReAct 循环 ⭐ 本周分水岭

**目标：不依赖任何框架，写出带终止条件的 Agent 循环。**

> 今天不要看 LangChain、不要看 LangGraph。手写。

### 动作

新建 `backend/app/core/react_agent.py`，核心结构大概是这样（伪代码，自己写成真代码）：

```python
MAX_STEPS = 8

async def run(question: str) -> dict:
    messages = [{"role": "system", "content": REACT_PROMPT},
                {"role": "user", "content": question}]
    trace = []                      # 记录每一步，面试要展示
    for step in range(MAX_STEPS):
        resp = await llm.chat_with_tools(messages)
        if not resp.tool_calls:     # 没有工具调用 = 给出最终答案
            return {"answer": resp.content, "steps": step, "trace": trace}
        # 执行所有工具调用
        for tc in resp.tool_calls:
            result = execute_tool(tc.name, tc.args)   # 内部兜异常
            messages.append({"role": "tool", ...})
            trace.append({...})
    return {"answer": "达到最大步数仍未完成", "steps": MAX_STEPS, "trace": trace}
```

### 三个终止条件，一个都不能少

1. **拿到最终答案** —— 模型不再请求工具
2. **达到最大轮数** —— `MAX_STEPS`，防止无限烧钱
3. **重复动作检测** —— 连续两轮调同一个工具同样参数 → 判定卡死，退出

第 3 条是加分项，做了就是「我考虑过死循环」。

### 必须理解（面试必问）

- ReAct 和 Plan-and-Solve 的区别？（ReAct 边走边想；Plan 先出计划再执行）
- 为什么要有 `MAX_STEPS`？不加会怎样？
- `trace` 为什么要存？→ 可观测性，出问题能回放

### 验收

- [ ] 单工具问题能走通（问时间）
- [ ] 多工具问题能走通（需要先算数再查时间之类）
- [ ] 把 `execute_tool` 改成必定抛异常 → 循环能优雅退出，不崩
- [ ] 故意构造一个模型会反复调同样工具的场景 → 被重复检测拦住
- [ ] 能画出这 4 个终止分支的流程图

## Day 12 —— Rerank

**目标：接入 Rerank，看精度变化。**

### 动作

1. 理解两阶段检索：**粗排**（向量/BM25 快但糙）→ **精排**（Rerank 慢但准）
2. 接入方式（任选）：
   - API 方案：通义/Cohere 的 rerank 接口
   - 本地方案：`sentence-transformers` 的 Cross-Encoder 模型
3. 流程改成：检索 top 20 → Rerank → 取 top 5 给模型

### 必须理解（高频面试题）

| | Bi-Encoder | Cross-Encoder |
|---|---|---|
| 怎么算 | query 和 doc **分别**编码，算向量距离 | query 和 doc **拼在一起**送进模型 |
| 速度 | 快，可预计算 | 慢，必须实时算 |
| 精度 | 一般 | 高 |
| 用在哪 | 粗排（全库） | 精排（少量候选） |

## Day 15 —— MCP 协议

**目标：读懂 MCP，跑通官方示例。**

### 动作

1. 读 `5️⃣大模型书籍\MCP图解指南_Zh.pdf`（**1 天读完，别拖**）
2. 理解架构：
   - **Host**（Claude Desktop 这类宿主应用）
   - **Client**（宿主内部，负责和 Server 通信）
   - **Server**（你写的，暴露能力）
3. 三类能力：`tools`（可执行）、`resources`（可读数据）、`prompts`（模板）
4. 传输方式：`stdio`（本地）vs `HTTP/SSE`（远程）
5. 跑通一个官方示例 Server

### 必须理解（高频面试题）

**MCP 解决什么问题？** —— 集成复杂度从 M×N 降到 M+N。
原来 N 个模型 × M 个工具 = M×N 个适配器；有了 MCP 协议，每个工具写一个 Server，任何支持 MCP 的客户端都能用。

**MCP 和 Function Calling 什么关系？**
Function Calling 是**模型能力**（模型知道要调函数）；MCP 是**工程协议**（工具怎么被标准化地暴露和发现）。两者互补。
