# Bad Case 分析报告：Agent 学习助手

> 定位：记录产品从「现象 → 定位 → 根因 → 修复 → 回归验证」的完整分析过程。
> 每个案例对应仓库中具名的回归测试，修复后全部固化为可重复执行的用例。
> 这套流程的设计原则：**Bad Case 不修则已，修一个就锁一个（回归用例），不允许同一个问题出现第二次。**

---

## Case 1：资料里没有的问题，模型"一本正经地胡说"

- **现象（Bad Case）**：用户问一个上传资料中根本不存在的知识点，模型流畅地编造了一段"看起来很像答案"的内容，且无任何来源标注。学习场景下这是最致命的错误——用户无法分辨真假。
- **定位**：复现后检查链路，发现该问题检索结果为空，但空结果仍被送入模型自由生成；模型默认动作是"回答"而不是"承认不知道"。
- **根因**：两层。① 流程层：检索空结果没有短路；② Prompt 层：没有给模型"退路"，模型没有"我不确定"这个默认动作。
- **修复方案**：
  1. 检索结果为空时**短路返回固定回退话术**（"资料库中还没有内容，或没有检索到相关片段"），不调用模型；
  2. 正常路径的 Prompt 采用「资料开始/资料结束」包裹 + 要求标注引用编号，把任务从记忆题改成阅读理解题；
  3. 事实问答 temperature 固定 0.1，减少发挥；
  4. 返回结构增加 `used_context` 标志，前端可区分"有依据回答"与"回退"。
- **回归验证**：空检索路径单测覆盖（不调用模型、话术固定、标志位正确）。

## Case 2：换个问法就检索不到（召回失效）

- **现象**：用课件原文关键词提问能命中，换口语化说法（同义改述）就查不到；反过来，精确术语查询用纯向量检索又排不到前面。
- **定位**：分别用精确词和改述句跑单路检索，确认 BM25 强在精确词命中、向量强在语义改述——**任何单路检索都只覆盖一种提问风格**。
- **根因**：单一检索信号无法同时覆盖"原文复述"与"语义改述"两类真实用户问法。
- **修复方案**：实现混合检索——BM25 与向量双路召回，RRF（Reciprocal Rank Fusion）融合排序；RRF 只看排名不看原始分值，天然规避两路分值刻度不可比的问题；中文分词用 bigram 处理保证"大模型"这类词可精确命中。
- **回归验证**：`test_bm25_wins_on_exact_term` 与 `test_vector_wins_on_paraphrase` 成对固化（两种风格各自必须命中），另有 `test_rrf_ignores_score_scale`、`test_hybrid_merges_both_signals` 锁住融合行为。

## Case 3：Agent 陷入死循环，请求永不返回还持续烧钱

- **现象**：某类问题下模型反复调用同一个工具、传同样的参数，循环不终止——请求悬挂，token 持续消耗。
- **定位**：trace 记录显示每步工具调用与参数完全一致，模型没有从工具结果中获得"下一步"信息，陷入复读。
- **根因**：Agent 循环缺少终止保护。原理上模型行为是非确定性的，必须有外层硬性护栏。
- **修复方案**：双重护栏——① `max_steps` 硬上限，到达即终止（stopped_by=max_steps）；② **重复动作检测**：将"工具名+参数"规范化后比对，重复即终止（stopped_by=repeat）；比对时忽略 JSON 键序，避免假阴性。
- **回归验证**：`test_stops_at_max_steps`、`test_stops_on_repeated_action`、`test_repeat_detection_ignores_key_order`、`test_different_args_not_treated_as_repeat`（参数不同不算重复，防止误杀合法重试）。

## Case 4：工具执行出错，整个请求 500

- **现象**：工具内部抛异常（文件不存在、表达式非法）时，异常沿调用栈炸掉整个请求；模型传了坏 JSON 或不存在的工具名时同样崩溃。
- **定位**：日志显示异常发生在工具执行层，且未做边界隔离——把"工具失败"当成了"服务失败"。
- **根因**：概念混淆。**模型只是"返回一个 JSON 说它想调什么"，执行方是我们**——执行失败应该作为信息回传给模型让它自行决策（换参数/换工具/告知用户），而不是当成服务端故障。
- **修复方案**：
  1. 统一 `ToolResult` 返回结构（ok/content/error），错误格式化为 `[工具执行失败] {error}` 回填 role=tool 消息；
  2. 注册层前置校验：未知工具拒绝、参数非 object 拒绝、必填参数缺失拒绝、坏 JSON 拒绝；
  3. calculator 用 AST 白名单解析执行，路径类工具做路径穿越拦截——**安全不靠 prompt 请求，靠代码层兜底**（模型分不清系统指令与文档内容，提示注入必须代码层防）。
- **回归验证**：`test_tool_failure_is_fed_back_not_raised`、`test_unknown_tool_does_not_crash`、`test_bad_json_arguments`、`test_missing_required_argument`、`test_schemas_are_openai_compatible`。

## Case 5：模型服务不可用，系统无降级

- **现象**：模型 API 超时/异常时，请求直接以错误结尾，用户看到原始报错。
- **定位**：Agent 主循环对 LLM 调用失败没有捕获分支。
- **根因**：外部依赖（模型服务）必然偶发不可用，但链路把"依赖失败"等同于"请求失败"，没有降级语义。
- **修复方案**：捕获模型调用失败，优雅终止并记录 `stopped_by=error`，向上返回结构化的降级提示而非原始堆栈。
- **回归验证**：`test_model_failure_degrades_gracefully`。

## 方法论沉淀（这套流程的通用版）

1. **现象要用用户视角记录**（"它胡说"），定位要用系统视角复现（检索为空→仍进模型）
2. **根因追问到原理层**：Case 1 的根因不是"提示词不够严"，是"模型没有'不确定'的默认动作，必须由产品给退路"；Case 4 的根因不是"代码有 bug"，是"模型输出与执行责任的概念混淆"
3. **修复必须先写回归用例**：用例名即验收标准，修复后永久驻留，任何后续重构不敢轻易破坏
4. **Bad Case 库 = 产品的免疫记忆**：回归测试套件中相当比例的用例源自真实踩坑，新需求开发前先查"这个场景有没有既有用例"
